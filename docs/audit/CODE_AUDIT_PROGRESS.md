### Этап 2 — построчный аудит, предварительные находки

Статус: в работе.

Найдены кандидаты на исправление/оптимизацию:

1. **Гонка/нестрогая синхронизация в main state.**  
   `requestPending` проверяется вне critical section, а `identifyActive` записывается из Zigbee callback и читается из loop без общей синхронизации. На ESP32 это обычно работает из-за размера типов, но формально это межзадачный data race. Будет исправлено без блокирующих операций в callback.

2. **Лишнее состояние в ZigbeeLight.**  
   Поле `identifyActive_` записывается, но нигде не читается. Это мёртвое состояние и будет удалено.

3. **Лишние пробуждения main loop.**  
   Loop просыпается каждые 10 мс даже после подключения Zigbee, хотя оптический движок событийный и получает Zigbee-команды напрямую. Можно снизить частоту housekeeping без ухудшения реакции маяка на Zigbee.

4. **Лишние critical sections в BeaconEngine hot path.**  
   `cycleEpochUs_` обслуживается только задачей BeaconEngine, однако вокруг его чтения/записи есть критические секции. Их можно убрать, сохранив синхронизацию только для полей, реально читаемых из других задач.

5. **NVS пишет оба ключа одновременно.**  
   При изменении только яркости или только On/Off сохраняются оба значения. План: отслеживать последнее подтверждённое состояние и писать только изменившийся ключ, сохраняя dirty при ошибке записи.

6. **Потенциал снижения CPU frequency.**  
   ESP32-H2 поддерживает штатные частоты ниже 96 МГц; это может снизить активное потребление без перевода Zigbee в sleepy mode. Изменение будет только конфигурируемым и попадёт в ветку после проверки сборки/CI. Аппаратная проверка обязательна перед merge.

7. **RGB обновляется до 200 раз/с во время вспышки.**  
   Для визуально плавной индикации 100–125 Гц достаточно. Это кандидат на снижение количества вызовов `rgbLedWrite`, но изменение будет принято только если не нарушает визуальную плавность.

8. **Battery float math выполняется редко.**  
   Переход на fixed-point возможен, но выгода мала: всего одна серия измерений в минуту. Приоритет низкий, чтобы не ухудшать калибровку ради микроскопической экономии.

9. **Sleepy Zigbee пока не включать.**  
   Основной потребитель энергии — постоянно включённый 802.15.4 RX. Однако перевод `RxOnWhenIdle=false` меняет задержку команд. Это не будет сделано скрытно в рамках оптимизации; текущая отзывчивость сохраняется.

### Ограничения, которые нельзя нарушать

- Период: `16.500000 s`.
- Последовательность: три вспышки `Fl(3).W.16.5s`.
- Текущая LUT-огибающая не меняется без отдельного обоснования.
- Рабочая частота внешнего LED PWM: 1 кГц, проверена на реальном модуле.
- Zigbee остаётся стандартным HA/ZCL без подмены сторонних model ID.
- Текущий режим радио — always-on End Device; переход в sleepy mode возможен только как отдельное решение после оценки задержки управления.


### Контрольная точка — реализация этапов 2–11

Статус: изменения сохранены в ветке, валидация сборкой ещё не выполнена.

#### BeaconEngine / hot path

- Удалено неиспользуемое поле `activeLevel_`.
- Убран второй вызов `esp_timer_get_time()` при применении нового состояния: timestamp теперь передаётся из task loop.
- Убраны critical sections вокруг `cycleEpochUs_` в `serviceAt()`: это состояние принадлежит только задаче BeaconEngine.
- Убран лишний `esp_timer_stop()` из `armDeadline()`; таймер уже останавливается в одном месте перед обслуживанием события.
- `writePwm()` теперь прекращает работу раньше, если PWM/RGB-состояние действительно не изменилось.
- Сохранён механизм повторной попытки RGB после throttle: если целевой RGB не был записан, ранний выход не срабатывает.
- Исправлена гонка фоновой работы на старте новой вспышки: `isDarkWindowSafe()` учитывает pending request и просроченный/ещё не опубликованный deadline.
- Публикация нового состояния BeaconEngine и сброс pending request теперь атомарны относительно проверки безопасного тёмного окна.

#### Main / синхронизация

- Убраны `volatile` у данных, которые должны синхронизироваться mutex/critical section.
- `requestPending` теперь проверяется и потребляется внутри одного critical section.
- `identifyActive` синхронизирован между Zigbee callback и main loop.
- Удалено неиспользуемое внутреннее `identifyActive_` из `ZigbeeLight`.

#### Zigbee CurrentLevel

При изучении реализации Arduino-ESP32 `ZigbeeDimmableLight` найден важный источник прежнего сброса яркости:

- библиотека записывает входящий `CurrentLevel` в свой внутренний `_current_level` **до** пользовательского callback;
- если координатор посылает `OFF + CurrentLevel=0`, одного исправления значения только в нашем callback недостаточно;
- последующий ON может снова вернуть этот внутренний ноль.

Исправление:

- нулевой уровень не становится remembered brightness;
- queued correction сохраняет последний ненулевой уровень;
- запись обратно в Zigbee endpoint выполняется из обычного main context через `ZigbeeLight::service()`, а не внутри callback, чтобы не пытаться повторно захватить Zigbee stack lock;
- ON+0 также трактуется как stale zero и не стирает remembered brightness.

#### NVS / ресурс flash

- Вместо одного общего `prefsDirty` используются отдельные `prefsOnDirty` и `prefsLevelDirty`.
- Если изменился только On/Off, уровень больше не переписывается; если изменилась только яркость, On/Off не переписывается.
- Ошибка NVS-записи больше не приводит к tight retry loop: следующая попытка откладывается.
- Проверяется результат `Preferences::begin()`; при отказе устройство продолжает работу с defaults без persistence.
- Factory reset корректно закрывает Preferences handle.
- Coalescing delay уменьшен с 1500 до 750 мс. Благодаря отдельным dirty-флагам это улучшает сохранение последнего пользовательского состояния после внезапного отключения питания без записи flash на каждую промежуточную команду слайдера.

#### Battery / ADC

- Масштабирование ADC переведено с float на fixed-point.
- Добавлена защита от деления на ноль.
- Добавлен `BatteryTelemetry::needsService()`.
- Main больше не вызывает `beacon.isDarkWindowSafe()` каждые 20 мс только ради батареи, когда следующий ADC sample/report не нужен.
- 32 ADC sample и интервалы измерения оставлены без изменения: их уменьшение даёт слишком малую экономию ценой ухудшения фильтрации.

#### Power / CPU

- CPU target снижен с штатных 96 МГц до **64 МГц** через официальный Arduino-ESP32 API `setCpuFrequencyMhz()`.
- Частота 64 МГц поддерживается ESP32-H2; APB/802.15.4 работают независимо от выбранной CPU frequency.
- Main housekeeping: 10 → **20 мс**.
- Status/button housekeeping: 10 → **20 мс**.
- RGB write throttle: 5 → **10 мс** (до 100 Гц), при этом основная PWM-огибающая остаётся с шагом 1 мс.
- Zigbee остаётся `RxOnWhenIdle=true`: не жертвуем мгновенной реакцией команд ради sleepy mode.
- Политика RX вынесена в `ZIGBEE_RX_ON_WHEN_IDLE`, чтобы дальнейший battery profile можно было сделать осознанно, а не скрытым изменением.

#### Что сознательно НЕ менялось

- `Fl(3).W.16.5s`, все длительности и LUT.
- PWM внешнего LED 1 кГц.
- 10-bit PWM.
- 32 battery ADC samples.
- always-on Zigbee RX.
- stack size BeaconEngine: без runtime high-water-mark уменьшать 4096 байт вслепую небезопасно.
- `-O2`: оставлен как текущий разумный компромисс performance/active time; агрессивные флаги LTO/`-fno-*` не добавлялись без полноценной сборки и измерений.
