# Независимый повторный глубокий аудит Doobsky ESP32-H2

**Дата:** 20 октября 2026
**Проверенный коммит:** `e841c971e1f2ab526cc6885862f1ca2f6b120403`
**Прошивка исходников:** `0.9.0-alpha.2`
**Статус:** аудит, **никаких правок исполняемого кода, COM3, флеш-памяти или Zigbee NVS не выполнено**.

## Объём и метод

Проверены полностью: четыре `src/*.cpp` (540 + 402 + 307 + 156 строк),
семь `include/*.h` (включая LUT и transition helper), два скрипта сборки,
`platformio.ini`, GitHub CI, `templates/spruthub/*`, Partition CSV
закреплённого Arduino-ESP32, тесты и аппаратно-значимые комментарии.
Всего в исходном исполняемом и сборочном коде: **13 файлов, 1718 непустых строк**.

Дополнительно проверены реальные исходники библиотеки **Arduino-ESP32 3.3.12**:
`ZigbeeDimmableLight.cpp`, `ZigbeeEP.cpp`,
`ZigbeeElectricalMeasurement.cpp`, `ZigbeeCore.cpp`.
Проверялись переходы между контекстами Zigbee task / Arduino loop /
BeaconEngine task, обработка ошибок, задержки, Zigbee ZCL/ZDO,
числовые границы, ресурс Flash/NVS и воспроизводимость сборки.

**Важно:** это углублённый статический/исходный аудит, не
полноценный runtime trace или независимое формальное доказательство.
Воспроизведение реальных ошибок Zigbee на отдельном ESP32-H2 ещё необходимо.

## Результаты: приоритет P1 (до аппаратного выпуска)

### P1-01. Физическая лампа меняется до подтверждённой записи Zigbee

**Источники:** `src/zigbee_light.cpp:59-63`,
`src/zigbee_light.cpp:102-126`, `src/main.cpp:311-319`;
upstream Arduino-ESP32 3.3.12
`libraries/Zigbee/src/ep/ZigbeeDimmableLight.cpp:69-91`;
`ZigbeeEP.cpp:77-90`.

**Подтверждение кодом.** Arduino `setLight(on,level)` сначала
обновляет `_current_state` и `_current_level` и запускает
`lightChanged()`, через который наш `onZigbeeLightChange()` меняет
`BeaconEngine`. Затем Arduino отдельно записывает OnOff и CurrentLevel
с помощью `setClusterAttribute()`. При любой неудачной записи возвращает
`false`, но тень состояния/выход маяка уже обновлены, а транзакция
не откатывается. В частности, при успехе OnOff и неудаче LevelControl
координатор и физическая лампа могут видеть разное состояние.

**Решение:** единый сериализованный путь изменения состояния; применять
выход только по результату подтверждённой локальной ZCL-операции (для
внешних команд — после разбора фактически принятого атрибута);
проверить обе фазы и откат/восстановление при ошибке.

**Тесты:** принудительный отказ записи OnOff, затем LevelControl;
вставить конкурентную входящую Zigbee-команду между фазами setter;
сверить `_current_state`, ZCL-атрибуты, `zigbeeLight.on()`,
`activeOn`, GPIO10.

### P1-02. Потенциальная гонка между Zigbee callback и локальным setter

**Источники:** `src/main.cpp:60-105,311-319`,
`src/zigbee_light.cpp:62-64,102-140`, библиотека
`ZigbeeDimmableLight.cpp:35-58,69-98`.

**Факт:** наша оболочка использует `mux_` для `on_` / `level_`,
но поля Arduino `_current_state` и `_current_level` меняются до
взятия Zigbee-lock внутри `setClusterAttribute()`; Zigbee callback
способен менять эти поля из другого контекста. Состояние существует
в пяти местах: Arduino ZCL shadow, ZigbeeLight shadow, main active state,
BeaconEngine request/active и NVS. Согласование не транзакционное.

**Статус:** реальная небезопасная последовательность в исходниках;
воспроизводимый runtime data race ещё не доказан.

**Решение:** очередь запросов с номером поколения и единым владельцем
ZCL-состояния; локальные кнопки обрабатывать через эту очередь,
не вызывать Arduino setter параллельно с remote callback.
Проверить инвариант `latest command wins`.

### P1-03. Отправка battery report считается завершённой без доставки

**Источники:** `src/battery_telemetry.cpp:350-372`,
upstream `ZigbeeEP.cpp:115-140` и `ZigbeeElectricalMeasurement.cpp:270-299`.

**Факт:** `reportBatteryPercentage()` и `reportDC()` возвращают успех,
когда SDK принял вызов `esp_zb_zcl_report_attr_cmd_req`.
Ни подтверждение доставки до координатора, ни актуализация состояния
Sprut.Hub этим не доказаны. Однако уже ставятся
`batteryTelemetryDirty_=false` и
`batteryReportInitialized_=true`. После возможной потери отчёта
следующий отчёт отправится лишь при следующем значимом изменении
или через период 300000 мс.

**Решение:** различать «поставлено в очередь» и «получено»;
сверить ACK/delivery callbacks библиотеки либо использовать
периодическое чтение/Configure Reporting на координаторе.
Не считать API `bool` сетевой квитанцией.

### P1-04. Неудача одного из двух отчётов вызывает повтор обоих каждую секунду

**Источники:** `src/battery_telemetry.cpp:303-372`,
`include/config.h:64-69`.

**Факт:** если, например, `reportBatteryPercentage()` возвращает
`true`, а `reportDC()` постоянно `false`, код оставляет
`batteryTelemetryDirty_` и каждую секунду повторяет ОБА report.
Эта ветвь воспроизводится логически без аппаратуры.
При деградации Zigbee может создавать лишнюю очередь APS.

**Решение:** отдельно отслеживать результаты двух отправок;
retry только неудавшегося атрибута; ограничить повторы backoff
1/2/4/8/30 секунд и счётчиком ошибок. При восстановлении
координатора сделать принудительный целостный snapshot.

## Приоритет P2 (надёжность, диагностика, совместимость)

### P2-01. В callback ZDO остался блокирующий Serial

`src/main.cpp:231-235`: `coordinatorProbeCallback()` напрямую
вызывает `Serial.printf()` в контексте Zigbee.
Если USB UART занят, возможна задержка стека. В light callback такой
антипаттерн уже устранён.

**Решение:** записывать результат ZDO в ограниченную очередь/структуру
под коротким критическим участком, выводить в `loop()`.

### P2-02. LightTrace — один слот: быстрые промежуточные события теряются

`src/zigbee_light.cpp:118-138`,
`src/main.cpp:516-531`.
Каждый callback перезаписывает `lastTrace_`; loop опрашивает
приблизительно каждые 20 мс. Если 2+ атрибута/команды пришли за период,
в логе останется только последнее событие. `seq` позволит заметить
пропуск, но не восстановить историю. Нельзя использовать этот журнал
для доказательства отсутствия ZCL-команд.

**Решение:** ring buffer фиксированной длины и счётчик dropped;
снимать исходный EP/cluster/TSN только там, где SDK реально предоставляет
их (не придумывать).

### P2-03. Отдельное локальное изменение не гарантирует push в Sprut.Hub

`src/zigbee_light.cpp:62-64` вызывает только Arduino `setLight()`.
В нём локально устанавливаются ZCL-атрибуты, но нет явного
`report OnOff` и `report CurrentLevel` на соответствующем binding.
Coordinator может обнаружить изменение через опрос или собственный
Configure Reporting, но этого нельзя предполагать без проверки.
Физически включённый маяк может оставаться `OnOff=false` в кэше UI.

**Решение:** исследовать binding/configure reporting на EP2 и
реальное событие после кнопки; сделать изменение стандартно reportable
без избыточных пересылок.

### P2-04. Sentinel уровня `0xFF` превращается в 100% яркость

`src/zigbee_light.cpp:102-105,148-155`:
`normalizeLevel(255)` выдаёт `DEFAULT_LEVEL=254`.
Для недействительного/неизвестного incoming LevelControl значение
заменяется полной яркостью, а не «значение неизвестно».
`ON+0` оставляет `OnOff=true`, хотя оптический выход погашен.
Эти решения требуют явной политики и тестов на комбинации
OnOff/LevelControl и order of attribute updates.

**Решение:** не трактовать `0xFF` как реальную команду 100%;
отделить invalid/unknown от пользовательской команды.

### P2-05. Нет атомарного обновления BinaryInput PresentValue/StatusFlags

`src/battery_telemetry.cpp:99-111`: два последовательных вызова
`setClusterAttribute()`, каждый отдельно берёт Zigbee lock.
В промежутке координатор теоретически может увидеть
`PresentValue=true` и `Fault=true` или обратное.
Для DIY допускается кратковременное рассогласование; для строгих тестов
нужна согласованная публикация обоих атрибутов.

### P2-06. Физический источник питания и логика Sprut Battery классификации

`src/battery_telemetry.cpp:24-32`,
`src/zigbee_light.cpp:17-29`,
`src/main.cpp:395-439`,
`include/config.h:50-52`.
Оба endpoint объявляются батарейными, тогда как RX всегда включён.
Это допустимая концепция rechargeable End Device, не доказанный баг.
Но ранее Sprut.Hub изменял `powerMode` на `BATTERY`, а затем имел
тайм-ауты чтения. Причинная связь не установлена. Требуются логи
actual TX/RX Zigbee и проверка ZDO Node/Power Descriptor.

### P2-07. Неинициализированная структура report в библиотеке

Upstream Arduino-ESP32 3.3.12
`ZigbeeElectricalMeasurement.cpp:270-291`:
`esp_zb_zcl_report_attr_cmd_t report_attr_cmd;` создаётся без
нулевой инициализации, затем заполняется лишь часть полей.
В отличие от `ZigbeeEP::reportBatteryPercentage()`, где структура
обнуляется. **Это код библиотеки, не наш.**
Риск зависит от того, какие дополнительные поля читает ZBOSS.
Нужна проверка документации SDK/пакета или отдельный безопасный
обёрточный вызов с zero-init; не утверждать, что именно это
уже вызвало сетевые тайм-ауты.

### P2-08. Battery unknown UI не фильтруется шаблоном

`src/battery_telemetry.cpp:9-10,198-225` выдаёт корректные
ZCL unknown: `0xFF` и `-32768`; шаблон
`templates/spruthub/Doobsky-DBL-BAT-CONTROL-v3.json` применяет
только `0.5` / `0.001` без правила скрытия unknown.
На USB при отключённой батарее UI может выдавать 100%/0В.
Проверять именно возможности runtime Jackson Sprut,
не полагаться только на его `schema.json`.

## Приоритет P3 (улучшения, а не доказанные неисправности)

### P3-01. Стартовый ADC усредняется без временного интервала

`src/battery_telemetry.cpp:115-124,226-254`: 32 чтения
`analogReadMilliVolts()` выполняются вплотную в `while`
до запуска Zigbee. Это усреднение шума, но не 32 независимых
по времени измерения. Явная `analogSetPinAttenuation` не задаётся,
используется default Arduino. Полезно сделать калибровку по
эталонному напряжению и тест с USB-only / нагрузкой.
Не добавлять длительную задержку до регистрации без оснований.

### P3-02. Диагностика Serial всегда компилируется в производственный образ

`src/main.cpp:187-305,515-530`, `include/config.h:43-46`:
30-секундный heartbeat, ZDO-ping и serial parser нужны сейчас
для отладки; после верификации Sprut разумно выделить
`DOOBSKY_DIAGNOSTICS` profile/flag. Это уменьшит вывод в USB
и сложность runtime, но удалять его **до** выяснения удалённого
управления нельзя.

### P3-03. Несколько зеркал состояния являются архитектурным долгом

`ZigbeeDimmableLight::_current_*`, `ZigbeeLight::on_/level_`,
`main.cpp::activeOn/activeLevel`, `BeaconEngine::requested*`
и Preferences: не являются мёртвым кодом, потому что служат разным
задачам. Опасность в отсутствии формального инварианта и generation ID.
Записать явную схему владения, обратной связи и переходов.

### P3-04. Неиспользуемые flash-разделы — НЕ лишний код

`platformio.ini:10` берёт `zigbee.csv` из
закреплённого Arduino пакета. Реальная таблица: app0 0x10000,
app1 0x150000, spiffs 0x290000, zb_storage 0x3EB000,
zb_fct 0x3EF000. Даже если OTA/app1 и SPIFFS сейчас не используются,
их удаление **не ускорит исполнение** и требует изменения
partition table, опасного для действующей Zigbee NVS.
Не оптимизировать эти разделы на работающем устройстве.

### P3-05. Манифест сообщает Git HEAD даже для изменённого дерева

`scripts/build_firmware.py:118-153`: фиксирует
`git rev-parse HEAD`, но не состояние `git status --porcelain`
и не git-diff hash. Локальная сборка с незакоммиченными изменениями
может быть подписана старым hash коммита. Добавить `dirty`
и SHA исходников, либо блокировать production build для dirty tree.
Сейчас манифест содержит SHA самого бинарника, что сохраняет
основную проверку целостности.

### P3-06. Гарантия патча Zigbee Core зависит от text replacement

`scripts/build_firmware.py:65-110` временно изменяет общий пакет
Arduino и восстанавливает исходные байты в `finally`.
Захват directory-lock защищает от двух штатных сборок, но при
принудительном завершении процесса останется lock и, возможно,
временно патченный SDK. В обычной успешной сборке всё
восстанавливается, что подтверждено CI. Защитить от stale lock
и проверять SHA фактического patch+original перед созданием релиза.

### P3-07. Световая характеристика не подтверждена эталонной осциллограммой

`include/config.h:84-102`, `src/beacon_engine.cpp:164-230`,
`include/flash_envelope_lut.h`.
Размер LUT = **354**, диапазон 0..1023,
требование `ceil(353571/1000)=354` соблюдено;
out-of-bounds при заданном тайминге не найден.
Суммарный период `16 500 000 мкс` тоже проверяется static_assert.
Однако длительности отдельных вспышек реконструированы;
нужны внешний фотодатчик/осциллограф и сравнение с требованием.

### P3-08. BOOT GPIO9 и фабричный сброс

`src/main.cpp:321-377`, `include/config.h:31-34,103-109`.
Кнопка коротко переключает маяк, удержание 5 секунд инициирует
`Zigbee.factoryReset()`. Это действующая функция, а не рудимент.
Однако удержание GPIO9 при перезапуске ESP32-H2 может войти в
ROM/USB_BOOT. Пользовательский сценарий сброса и USB-диагностики
должен учитывать strap pin.

## Что проверено и НЕ признано дефектом

- Нет дубликатов реализаций функций; `localToggle()` в
  `src/main.cpp` встречается дважды потому, что первое — декларация.
- `BeaconEngine` отделён от Zigbee: выход не записывает ZCL напрямую.
- `BeaconEngine::isDarkWindowSafe()` проверяет pending,
  `lastPwmDuty_` и время следующего deadline; замысел не удалять.
- Предел `FLASH_ENVELOPE_LUT` и 3x flash cycle согласованы с константами.
- `BinaryInput` EP1, Battery Voltage/Percentage и DCVoltage
  — функциональные кластеры, не рудименты.
- `ZigbeeCore` после каждой нормальной сборки восстанавливается,
  профили Strict/Sprut разделены и совместимость NWK AES сохранена.
- Legacy TEST/POWER-v4 и заводской install-code generator уже удалены
  предыдущим аудитом; восстанавливать их не требуется.
- Отдельный Zigbee 3.0 strict профиль может быть полезен для тестов,
  но домашний Sprut-совместимый профиль нельзя называть
  сертифицированным или гарантированно совместимым с любым TC.

## Ограничения существующих тестов

Предыдущий Windows прогон: **81 тест, 80 passed, 1 skipped**;
GitHub Actions run **#126** для проверенного commit завершился SUCCESS.
Однако большинство Python тестов — проверки наличия строк,
порядка вызовов и конфигурационных значений.
Они НЕ вводят реальные ошибки `setClusterAttribute()`,
не эмулируют конкурентный Zigbee callback и кнопку,
не подтверждают APS delivery и не измеряют PWM физически.
Прохождение CI не снимает P1/P2 замечания.

## План исправления без риска Zigbee NVS

1. Создать тестируемый адаптер ZCL операций с inject-able ошибками
   и тестом двумерного результата OnOff/Level; сохранить EP1/EP2.
2. Сериализовать local/remote state transitions, добавить sequence number
   и authoritative state; тесты на bursts с разными порядками событий.
3. Разделить очередь reporting батареи, отделить queue success от
   delivery, ограничить повторные попытки.
4. Исправить ZDO callback logging и диагностику потерь событий.
5. Проверить/добавить конфигурацию reporting для OnOff и CurrentLevel;
   сравнить физическую лампу и actual ZCL чтение после кнопки.
6. Отдельно исправить правило unknown в шаблоне Sprut после
   проверки поддерживаемых операторов runtime.
7. После host-tests и обеих сборок — испытать на отдельном ESP32-H2.
   Только потом обсуждать app-only flash на COM3, никогда не стирать NVS
   и сохранить текущий полный 4MB backup.

**Вывод:** серьёзных дубликатов мёртвого runtime-кода не найдено;
основные риски сейчас не в «лишних строчках», а в обработке
конкурентных команд Zigbee, результатов сетевой отправки и ошибок
сторонней Zigbee-библиотеки.
